# Examples

- `config.example.json`: a wev configuration with a remote inventory (one staging and one production host, both read-only). Check it with `wev config validate examples/config.example.json`. To use it, copy it to `wev.config.json` at the repository root, or pass it with the global `--config` option on `wev run start`: the run pins the configuration then, and a later command with a different `--config` is refused. The aliases are placeholders; real aliases come from your own SSH config. The file sets `language` explicitly, which then takes precedence over the `LANG` environment variable (not over `--lang` or `WEV_LANG`); delete the key to leave the choice to `LANG`. The `decision.jev.command` value `/absolute/path/to/jev` is a placeholder and only matters if you set `decision.provider` to `jev`: use the absolute path of your JEV client (a bare `jev` is looked up only in `permissions.exec_path`, which holds system directories by default, so a JEV in `~/.local/bin` is not found by name; `wev config validate` warns when the program does not resolve).
- `plan.example.json`: a two-task plan for `wev plan set --file`, run inside an active run (`wev run start` first). The second task depends on the first, so the engine offers them one after the other. Each check is an object that ties the command to the criterion it proves (`"criteria": [0]` is the zero-based index of the acceptance criterion). A check written as a plain string is accepted but is untied and is labeled so. The `make test` command is a placeholder for your project's real check; a check that already passes before the task changes anything does not verify the task.

Both files are validated against the engine's schemas by `tests/unit/test_skills.py`.
