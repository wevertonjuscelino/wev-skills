# Security policy

Portuguese version: [SECURITY.pt-BR.md](SECURITY.pt-BR.md).

## Supported versions

| Version | Status |
|---|---|
| The latest release (see the [releases page](https://github.com/wevertonjuscelino/wev-skills/releases/latest)) | Receives security fixes. |
| Any older release | Not patched. Upgrade to the latest release. |

Every release is a full, final release published from `main`; there are no maintenance branches.

## Reporting a vulnerability

Do not open a public issue for a vulnerability.

- Use GitHub's private vulnerability reporting on this repository: the Security tab, then "Report a vulnerability", or <https://github.com/wevertonjuscelino/wev-skills/security/advisories/new>.
- The owner has to enable that feature in the repository settings. If the "Report a vulnerability" option is missing, it has not been enabled yet; in that case open a public issue that asks for a private way to reach the maintainer and contains no detail of the vulnerability.
- No email address is published for reports.

Include what you found, the steps or command to reproduce it, the version or commit, and the impact you expect. Do not include real secrets or private data. This is a one-person project; there is no committed response time, but reports are read and acknowledged.

## Threat model

wev-skills is a guardrail for a fallible agent and a recorder of decisions. It is not a security boundary against an adversarial agent.

The reason is structural. The engine runs in the same user account as the agent it constrains. Inside one account the CLI cannot authenticate who is typing, and every file the engine keeps (run state, approvals, audit log, configuration) can be rewritten by the agent with its own tools. No key stored in that account would change this, because the agent could read the key too.

What follows from that:

- The engine catches mistakes: a destructive command run by accident, a command in the wrong mode, a secret pasted into a log, a remote start on the wrong host.
- The human gate that exists is Claude Code's own permission prompt. The plugin's `PreToolUse` hook answers `ask` for the sensitive Bash command lines it can read, and the person's answer in that prompt is the approval for that call. A command line it cannot read (the inside of a script file or of a program) is not asked about; see "Known limits".
- Without the plugin's hooks, approvals are records, not gates. `wev approval grant` asks for a terminal and a typed word, which a determined process can supply through a pseudo-terminal.
- An agent that sets out to defeat the engine can. Isolation has to come from outside: a container, a separate user, operating-system permissions, the permission settings of the agent platform.

### In scope for reports

- The Python engine in `src/wev_skills/` and its CLI (`wev`), the hooks in `hooks/hooks.json`, the scripts and the workflows in this repository.
- A mistake-class bypass of a control listed under "What each control does": a command the classifier should recognize and does not, a hook that stays silent where this document says it asks, a secret shape that redaction says it covers and misses.

### Out of scope

- Anything listed under "Known limits".
- Vulnerabilities in Claude Code, tmux, OpenSSH, Python or other software the project calls; report those to their maintainers.
- Findings that need an attacker who already controls the machine or the user account, beyond what this document already states an agent in that account can do.

## What each control does

### The Bash hook (`wev hook pre-tool-use`)

- Judges each Bash command under the active run's pinned configuration, mode and risk. It answers `deny` or `ask`, never `allow`, and it never reads the approval store: a destructive command is `ask` every time.
- Without a run, judges the command under the built-in default policy (the defaults of the engine, with the state directory protected) in execute mode at medium risk, rooted at the git top-level of the hook's directory, or that directory outside a repository. A repository configuration is not read in that case: a file in the tree must not loosen the guard when no run pinned a configuration. Approvals and loop detection apply only inside a run.
- Finds the run from the hook's directory and from every path the command names, so a command started in `/tmp` or in a nested repository that touches a run's tree is judged by that run. `cd`, `pushd` and `git -C` are followed. On macOS and Windows these paths are compared with the registry's roots without case when the file system confirms the same place (a case-sensitive volume keeps `Repo` and `repo` apart, and a path that does not exist matches only as written); on Linux, exactly. It trusts only a run that the per-user registry (`$XDG_STATE_HOME/wev-skills/active-runs.json`, else `~/.local/state/wev-skills/active-runs.json`) lists by root, state directory and run id; `run start` writes that entry before it creates the run, and fails (`registry_unwritable`, exit 5) when it cannot. An open run found in the tree that the registry does not list (a `.wev/` shipped inside a repository, a lost or rewritten registry entry, an entry naming another run id) is not used for policy: its state file is read only for its phase, and every Bash command gets `ask`, except what the built-in default policy denies, which stays `deny`. A registry file that exists but cannot be read or parsed gets the same answer; an absent registry means no registered runs. The hooks that print the plan brief print nothing in those cases. The registry's directory (`wev-skills` under the state home) is a protected path for the hook, with or without a run, matched by path whether it exists or not. The hook judges Bash commands that name that directory or a path under it (a read, a write, a redirection, a copy or link onto it, `mkdir` of it) and moves or removals of a directory above it, including one reached through a symlink (see the ancestor bullet below). Known limits: extracting an archive or copying into a directory above the registry (`tar -xf` run inside the parent, `ditto`, `cp -r x/. <parent>/`, `rsync` into the parent), or copying, linking or moving a tree onto a missing directory above it (`cp -r forged ~/.local` after `~/.local` was moved or removed with approval), is not caught when the command does not name the protected path, and the agent's own file tools can edit the registry (see "Other tools").
- Answers `ask` (and `deny` in plan mode) for any environment assignment before a command, for `env`, and for `export` and similar shell words.
- Answers `ask` for anything it cannot read with certainty: parameter and command expansion, `$'...'` and `$"..."` quoting, globs, brace lists, `~user`, `eval`, `source`, `exec`, `command`, `builtin`, `script`, `expect`, `xargs`, `find -exec`, `git -c`, `git --exec-path`, `git --config-env`, `git -C` outside the run root, a shell running a script file, and one argument that holds a whole command line.
- Answers `ask` for these engine commands when the command line is one it can read: `approval grant`, `approval deny`, `approval request` (with or without `--reopen-denied`, because a run is active), `guard acknowledge`, `task reopen`, `specialists accept`, `specialists retire`, `specialists score`, `run adopt`, `run start`, `run finish`, `agent create`, `agent export`, `remote start`, `remote stop`, `jev key set` (it writes the JEV key file), `jev ask` and `jev batch` (they send the content of a file to the JEV service, and `jev batch` overwrites its `--out` file; `jev status` is not asked) and anything carrying `--config`, with or without a run. It recognizes them by words wherever they appear: the engine's launcher by real path, the bare word `wev`, or `-m wev_skills`, followed by the sensitive subcommand. This holds when the engine is called directly, behind a wrapper the classifier knows (`nohup`, `nice`, `timeout`, `time`, `stdbuf`, `setsid`, `env`, `xargs` and the rest of its wrapper list), inside an inline `sh -c`, `bash -c` or `zsh -c` script, or as arguments handed to another program. The exemption from the ordinary policy still applies only to a program that resolves by real path to the plugin's `bin/wev` or to the running interpreter with `-m wev_skills`.
- Also answers `ask` for `rm` with abbreviated long options (`--recursiv`, `--forc`), `git rm -r` or `-f`, any `git clean` that is not a dry run, `rsync --delete*` and `--remove-source-files`, and for a recursive reader (`grep -r`, `rg` with `--hidden` or `-uu`, `find`, `tar`, `zip`, `cp -r` or `-a`, `rsync -r` or `-a`) given a directory that contains a protected path. A direct read of the protected file is still denied. This is a heuristic over a fixed list of programs and options: it looks at directories that exist when the command is judged, walks at most 20,000 entries (a larger tree is treated as holding a protected path), does not read exclusion options, and `rg` without `--hidden` is not asked about hidden protected names because it skips hidden files. Operands are read as written and with a leading `~`, `~+` or `~-` expanded. `grep -r` and `rg` given only their pattern, and `find` given no operand, are treated as walking the working directory, even when the pattern names an existing file. The value of an option is counted as an operand, so `rg -g '*.py' x` and `find -name x` are not seen as walking it.
- Answers `ask` (`deny` in plan mode) when `mv` (its sources), `rm`, `rmdir`, `unlink`, `find -delete` (its start directories) or `rsync --remove-source-files` (its sources) moves or removes a directory that holds a protected path. A protected location is matched by path; a protected name (`.git`) is found by walking the directory, with the limits of the recursive-reader check. Moving a directory that holds `.git` therefore asks. A symlink operand is not walked, but it is matched by path as written and as resolved, so `mv`, `rm` or `unlink` of a symlinked `~/.local` asks. Any unambiguous prefix of `--target-directory` (`--t`, `--targ=x`) counts as naming the target, and then every operand is checked. The hook's shell check asks for every word starting with `~+`, `~-` or `~user`. Before protected paths are matched, a leading `~`, `~/`, `~+` (the working directory) or `~-` (`$OLDPWD`, when set) is expanded, and the word as written is checked too; a match in either spelling can only raise that `ask` to `deny`. `~user`, and `~-` without `$OLDPWD`, are checked only as written. On macOS and Windows, whose default file systems ignore case, protected locations are compared without case (`.LOCAL` reaches `.local`); on Linux they are compared exactly. Protected names (`.git`) are compared without case on every platform. The engine's own gate (`wev exec`) applies the same rule to its protected paths.
- Finds a run for `rm -rf <parent of the repository>` too: a path that is a parent of a registered run root counts as touching that run.
- Fails safe: an unreadable state, an internal error and a command too long to analyze become `ask`, with or without a run. Oversized or malformed input is `ask` when a run is known and silent without one, because the command is unknown and there is no run to judge it by.

### The engine's own gate (`wev exec`)

- Uses a run's pinned configuration as policy only when the per-user registry lists that run (state directory and run id). An open run found in the tree that the registry does not list, or any open run when the registry file cannot be read, is refused (`unregistered_run`, exit 5) by every command that applies policy: `exec`, `task`, `plan set`, `run resume`, `run report`, `run finish`, `guard check` and `acknowledge`, `check-command`, `approval request`, `approval grant` and `deny`, `remote preflight`, `start`, `status`, `capture` and `stop`, `specialists`, `agent create` and `export`, and `jev ask` and `batch`. `--run` does not bypass this. Reads still work: `run status`, `run brief`, `plan show`, `state show` and `state list` report `"registered": false` (`state list` as `active_registered`), and `approval list`, `show` and `verify`, `agent list`, `show` and `validate`, `config show`, `remote hosts` and `jev status` read without refusing. The phase is read from the run's own file, so a finished run is not checked against the registry; instead every command that changes the run or runs something refuses a finished run (`run_finished`) before anything else, and only `run report`, `run finish`, `guard check` and `task next` accept one. The human operator registers an open run with `wev run adopt`, which first shows its pinned configuration on single lines with terminal control characters removed. The agent's own file tools can still edit the registry (see "Other tools").
- Runs an argv without a shell. Refuses shell syntax, a leading `NAME=value`, and (in plan mode) anything that is not on the read-only list.
- In an execute run a command acts for a task that is `RUNNING`. `--task` must name a running task (a pending, finished or unknown id is refused, and the error names the running tasks). Without `--task` the only running task is used and the output says so (`task_implied: true` and a `task_note`). With no task running, or with several running and no `--task`, only read-only commands are accepted. So an agent's `may_mutate: false` and the task's risk do not depend on the caller naming the task. With two tasks running the caller still chooses which one a command is for; the engine cannot tell which agent is typing.
- An agent with `may_mutate: false` may run read-only commands, the task's own declared checks and the check commands discovered in the repository at `run start` (for example `make test`, `make lint`), by exact argv match; everything else is refused with `agent_read_only`. Those commands still go through the policy, so one that needs approval still needs it.
- Looks a bare program name up only in `permissions.exec_path`, never in `$PATH`, records the resolved path, and refuses a program that resolves inside the run's working tree. A program named by a relative path needs approval.
- Classifies commands as destructive, privileged, network, external-effect or unanalyzable, including unique-prefix abbreviations of git long options, git configuration given on the command line, unknown git subcommands, and wrappers such as `nohup`, `timeout`, `script` and `nice`.
- Denies a literal or glob argument that names a protected path (`.git`, the dot-env file, the state directory, and what the configuration adds).

### Approvals

- A grant covers one exact argv, in one resolved working directory, in one run (for a remote action, on one host alias). It is single-use, it expires after `permissions.approval_ttl_seconds` (default 900) and the execution that uses it consumes it.
- A denial is final for that action in that run. "The same action" for a denial means the same words in the same order within the same run: every token of the argv is split like a command line and blank tokens are dropped, so the working directory (`--cwd`), the stated risk, the reason, quoting, whitespace and how words are grouped into tokens do not produce a fresh request. `wev approval request` returns the denied record and `wev exec` answers denied. For a remote action the host alias is the first word, so a denial is per host. A new run starts clean. The comparison is on words and does not resolve paths (`build` and `./build` are different actions), and the record is a file in the agent's account (see "Known limits"). Only `wev approval request --reopen-denied`, a human-operator command that needs a terminal and the typed confirmation word, replaces it with a fresh pending request. A grant is unchanged: bound to the exact argv, the resolved working directory and the run (and host for remote), single use, expiring.
- An action whose text redaction would alter is refused instead of being shown masked, so the operator sees exactly what would run. Pass the secret through a file or an environment variable.
- `approval grant`, `approval deny`, `guard acknowledge`, `task reopen`, `specialists accept`, `specialists retire` and `run adopt` need a terminal on stdin and stdout, show the full action and ask for a word printed on screen. The record holds the operating-system user, the terminal device and the time. It does not hold an identity. A request records `requested_by`, a name the caller supplies (self-declared). A decision records the operating-system user, the terminal device and the time. Nothing compares the two, because inside one account the engine cannot tell requester from operator. `specialists score` is not one of these typed-word commands: Claude Code asks for it, the other harnesses deny it, and an agent never runs it. A lesson or retirement decided by score records `accepted_by` `score` and no person; it needs none of this friction (see "Unattended scoring").
- Tamper evidence: every decision is also appended to the audit log, a grant is honored only when a matching `approval.granted` event exists, and `wev approval verify` lists mismatches. This catches accidents and a grant written straight into `approvals.json`. It does not catch an agent that rewrites both files.

### Configuration and agents

- A run pins its configuration when it starts. Every command uses the pinned one and refuses a different `--config`. Commands outside a run print which source they used.
- `decision.jev.command` is `builtin` (the default, the built-in HTTP client below) or names an external program, which must be a bare program name (not a shell or an interpreter) or an absolute path outside the repository. `agents.directories` must stay inside the repository or the user's configuration directory. A spec outside the built-in catalog cannot reuse a built-in agent id unless `agents.allow_override` is set.
- `wev agent create` and `wev agent export` write only inside the repository, never into the state directory, `.git`, `.claude` or a protected path, and do not overwrite a file that is not already an agent spec or a generated subagent file. The one exception is `wev agent export --out .claude/agents` (exactly `<repository root>/.claude/agents`): only `<id>.md` files, never through a symlinked `.claude` or `agents`, and over an existing file only if it carries the generated-file marker; every other path under `.claude` stays refused. The check runs at call time and is a guardrail, not a boundary against an agent that can write files itself.

### Built-in JEV client

- The key is looked up in this order: the `TYPESAFE_API_KEY` environment variable, the file `.env` in the user's wev-skills configuration directory (`$XDG_CONFIG_HOME/wev-skills`, else `~/.config/wev-skills`), then the macOS keychain service `typesafe-api-key`. The key is never printed or put in a failure reason.
- That file is refused when group or others hold any permission on it (anything looser than mode 600). The lookup then stops with an error instead of moving on to the keychain.
- The default endpoint is `https://api.typesafe.ai/v1/systemone`. `JEV_API_URL` replaces it. A key stored in the user's env file or the macOS keychain goes as a Bearer header only when the endpoint's scheme, host and port are those of the default endpoint; for any other https host only a key from `TYPESAFE_API_KEY` is sent, and with only a stored key the call is refused (`key_not_for_endpoint`) before any request, `wev jev status` reports `harness` and `wev config show` warns. A `TYPESAFE_API_KEY` in the environment goes to whatever https host `JEV_API_URL` names. Only a loopback address may use plain http, and it gets no key. Redirects are not followed. Setting the variable in front of a command (`JEV_API_URL=... wev ...`) is an environment assignment, which the Bash hook answers `ask` (`deny` in plan mode); a value already in the environment is not seen by the hook.
- The state text is redacted before it is sent. The questions file is sent as written, without redaction.
- At most 1 MiB of a response is read; a longer one is a failure (`response_too_large`).
- The Bash hook answers `ask` for `wev jev ask` and `wev jev batch`, with or without a run. `wev jev status` makes no network call and is not asked.

Implemented and tested against a local fake server; the live service was not run.

### Remote module

- Hosts come from the run's inventory of SSH aliases, with strict host-key checking. Mode and risk come from the active run and cannot be widened on the command line. A task must be assigned to an agent with `may_use_remote`.
- Status reports PASSED or FAILED only with evidence that the session belongs to that task; otherwise UNKNOWN with the reason. Sessions the module did not create are left alone.

### Untrusted text and redaction

- Command output, remote capture and other external text are stripped of control characters and escape sequences and fenced as data before the CLI returns them. Pattern scanning for instruction-like text only informs.
- Redaction masks recognizable secrets in logs, audit records, guard events and approval records, including values after secret-named flags, `Authorization` headers, URLs with credentials or token-like query parameters, and well-known webhook URLs. It is best effort. Whole-argv redaction (the value after `--password`, credentials in URLs and similar) also applies on refused paths. `tests/integration/test_refused_redaction.py` searches every file under the state directory for a canary after allowed, denied, approval-required and guard-refused executions, for these event types: `exec.ran`, `exec.denied`, `exec.approval_requested`, `guard.tripped`, `task.checked`, `approval.requested` and `task.recorded`. In addition, any audit event that stores a list under the key `argv` is masked as one command line.
- Directories under the state directory are created with mode 0700 and files, including lock files, with mode 0600.

## Other harnesses

`wev harness install --target codex|gemini|opencode` puts the guard hooks into Codex, Gemini CLI and OpenCode. Status: implemented and tested with fake harness CLIs; not run against the real harnesses yet (e2e part). The same guardrail-not-boundary position applies.

- **Asks are reminders.** These harnesses have no ask decision for hooks. A policy `ask` of the guard (a command Claude Code would put to the person) becomes allow plus a warning (whether the agent sees it is unverified). Do not read an ask there as a gate. From probes of the hook, these run with only that warning: `git push`, `rm -rf build`, a word with a glob, a `$VAR` word, a line with an environment prefix (`X=1 cmd`), `wev run start|finish`, `wev ... --config`, and `wev jev ask|batch` (which sends file content to the JEV service). The warning goes to stderr on Codex, to `systemMessage` on Gemini CLI and to `reason` on OpenCode (likely never shown).
- **A deny can be routed around.** A deny is final for the line the guard reads, but the same target reached through a variable or a glob is an ask, so a warning: `D=.wev; rm -rf $D` was allowed with a warning on Gemini CLI. Read a deny on these harnesses as a stop for the plain form only. In the same way, an operator command hidden behind a variable (`c=grant; wev approval $c`) or built at runtime is not recognized there, so it runs with a warning. A line the guard cannot read (subshells, braces, heredocs, command substitution, very long lines) is denied on these harnesses; wrap such commands in a script or run them in your terminal. A command whose program word the shell rewrites (`$VAR`, `$'…'`, a brace list, a glob) is denied on these harnesses; a rewritten argument only warns.
- **Human-operator commands are denied.** `approval grant|deny`, `approval request --reopen-denied`, `guard acknowledge`, `task reopen`, `specialists accept|retire|score`, `run adopt`, `jev key set` and `harness install|uninstall` are a deny on these harnesses (`hooks.reason.person_only_denied`), wherever they appear on the line and with or without `--config`. Claude Code still asks for them. A person runs them in their own terminal. The exported skills open with a paragraph that says so. What the guard cannot read (a script file, a program that types the command) is not covered.
- **Fail-safe is deny.** An unreadable hook input, an internal error, an unregistered run, an unreadable run registry or an answer that cannot be parsed becomes a deny, not an allow.
- **Codex works under the session directory.** The Codex hook does not receive the workdir the model chose for a command (verified in the Codex source at rust-v0.160.0), so a command is judged as if it ran in the session cwd. Gemini CLI (`dir_path`) and OpenCode (`workdir`) send one, and the guard honors it; an invalid value is a deny.
- **OpenCode limits.** The guard is a plugin (`plugins/wev-guard.js`) that runs `bin/wev` without a shell and denies when `wev` cannot run. Its warning goes to `console.warn`, which likely never reaches the agent, so an OpenCode ask is in practice a silent allow. `spawnSync` blocks the plugin for up to 10 seconds per bash call. The manifest keeps unresolved paths, so a changed `XDG_CONFIG_HOME` makes `uninstall` refuse until it is restored. The plugin was tested under node with a fake `wev` and never run inside OpenCode.
- **The hook runs with the install interpreter.** Hook commands and the OpenCode plugin call `<python> <clone>/bin/wev`, with `python` the interpreter that ran `install` or `export`, because `bin/wev` under an older `python3` exits 0, which these harnesses read as allow. After a Python upgrade or a move of that interpreter or of the clone, run `wev harness install` again. When the hook cannot run at all: Gemini CLI treats a failed hook as a warning and the action proceeds (its note); Codex reports a hook error; the OpenCode plugin denies.
- **No session context on OpenCode.** The plugin wires only `tool.execute.before`, so the run brief that Codex and Gemini CLI get at session start is not injected on OpenCode (`skipped` says so).
- **A failed reinstall leaves no install.** `install` over a previous one undoes the previous install before it registers the new one; if registering then fails, the error carries `previous_removed: true` and nothing is installed: run `install` again.
- **Name collisions.** On Gemini CLI, `install` without a wev manifest refuses (exit 5) when `gemini extensions list -o json` already shows an extension named `wev-skills`, because a later `uninstall` would remove it. On Codex the shape of `codex plugin list` is unknown, so a plugin of yours named `wev-skills` is not detected, and `uninstall` would remove it.
- **Codex trust is yours.** Codex asks the person to trust hooks once; wev does not bypass that gate. Until you trust them, they do not run.
- **Gemini link consent is yours.** wev runs only `gemini extensions list -o json` (first install) and `gemini extensions validate`. The person runs `gemini extensions link` and accepts its security warning; wev never accepts it for them. Until then, no Gemini hook is installed.
- **The manifest is data, not instructions.** `uninstall` reads `$XDG_DATA_HOME/wev-skills/harness/<target>/manifest.json` only as a list: registrations are compared to fixed tuples, every file path must stay inside the target's directory, and symlinks are refused. It removes only what wev wrote. Anyone who can write the manifest can still make `uninstall` fail, and an agent in your account can edit the harness config files directly.
- **Out of scope.** A symlinked parent above the wev-owned data root is the user's own layout and is not defended against.
- **Asks on `install` and `uninstall`.** In Claude Code the hook asks before `wev harness install` and `uninstall`; `export` is not asked.

## Unattended scoring

`wev specialists score <id>` (and `score_on_finish`, off by default) starts the `claude` CLI without a person present, to run stored cases and to ask for lessons. Status: the engine side is implemented and tested with fake runners and fake agents; the real `claude -p` path is implemented but untested until the owner runs it.

- **What the unattended run may do.** `claude -p` is started with `--restricted`, `--strict-mcp-config`, `--plugin-dir <wev root>`, the six tools `Read,Edit,Write,Glob,Grep,Bash` (also as `--allowedTools`), `--permission-mode dontAsk` and `--no-session-persistence`. A lesson request uses the same safety flags, with no tools, no specialist system prompt and a fresh empty temporary directory as its working directory. The engine never passes `--dangerously-skip-permissions`, `--bare` or `bypassPermissions`, and refuses the run when the plugin manifest or `hooks/hooks.json` is missing. Bash inside the run goes through the wev hook: checked by hand on 2026-10-23 with Claude Code 2.1.302: inside such a run the wev hook blocked `wev approval grant`, `rm -rf` of repository directories and `git clean -fdx` (a manual check, not an automated test). The guard does not treat `git checkout <commit>` or `git switch --detach` without paths as destructive, so the agent can still move its worktree to another commit. Each agent run's event stream (`--output-format stream-json --verbose`) is kept, redacted and cut at 2,000,000 characters, as `.wev/score-logs/<score id>/<case>-<n>.jsonl`, so the commands the agent ran can be read afterwards.
- **Model-written lessons are untrusted text until scored.** A lesson is requested only from failed cases, at most `specialists.score_max_new_lessons` per run, with its inputs fenced and redacted. The engine refuses an answer that is not `{"lesson": "..."}` of 1 to 600 characters, or that has control or invisible characters, newlines, fence look-alikes, findings from the untrusted-text scan or a term from a fixed English list (`allowed-tools`, `permission`, `bypass`, `dangerously`, `--tools`, `tools:`, `model:`, `sudo`, `chmod`, `specialists accept|retire`); the list also drops some legitimate English lessons. A lesson enters only when no stored case loses a pass and the total rises; a tie stays `proposed`, and a losing or tied model lesson is not stored. It is shown only inside the untrusted-data fence.
- **A person's decision is final.** A lesson a person accepted or retired is not changed by score. A score retirement comes back as `proposed` at the next `specialists learn`. Score writes an audit event (`specialists.auto_accept`, `specialists.auto_retire`) before it writes the specialist.
- **The scored cases.** The agent runs in a scratch git worktree and each check goes through the engine's command policy with no grants, so a command that needs approval is refused, with a scrubbed environment (`PATH`, `HOME`, `LANG`, `LC_ALL`, `TMPDIR`). Cases must be committed and clean. After every agent run and every check the engine fingerprints the shared git directory (config, `config.worktree`, `hooks/`, `info/`, modes and times; a file over 1 MB fails closed) and stops with `git_config_changed` on any change; no git command runs in the workspace after the agent. Do not change git config during a score run (for example `git push -u` or `git branch --set-upstream-to`): the change aborts the run as tampering.
- **`score_on_finish` removes the person-only gate.** `specialists score` is person-only, but with `specialists.score_on_finish` true, `wev run finish` starts the same unattended `claude -p` runs for each specialist that ended a task, and `run finish` is not person-only (Claude Code asks for it; the other harnesses only remind). An agent that finishes a run then starts unattended scoring and spends tokens without that gate. That is why the key is off by default; turn it on only if you accept that.
- **Run it from a terminal or in the background.** A score run makes up to `score_max_runs` agent runs of up to `score_timeout_seconds` each, far longer than an agent's Bash call allows (Claude Code's Bash tool stops a command after 2 minutes by default, 10 at most). Run `specialists score`, and `run finish` with `score_on_finish`, from a terminal or in the background: a call that is killed mid-run leaves the tokens spent and a `wev-scoring-*` temporary directory behind. Before the first agent run the command prints the planned run count and the cap to stderr.
- **What this is.** The pin of the cases, the run cap (`score_max_runs`), the text filter and the score are guardrails for a fallible agent. They are not a boundary against an adversarial agent in the same account, which can edit `wev-specialists/` and `.wev/` directly. The residual risks are listed under "Known limits".

## Third-party skill updates

`wev skills` downloads and installs `rea`, `agent-skills` and `wev-skills`. Status: implemented and tested with a local fake registry, a fake npx and local tarballs; the real registries, downloads and the real rea server are not run in this change (e2e part). The same guardrail-not-boundary position applies.

- **Downloads are untrusted data.** Registry requests go only to `api.github.com` and `registry.npmjs.org`; tarball downloads go only to `api.github.com`, `codeload.github.com` and `github.com`; https only, and every redirect is checked against the same list. The tarball URL is built from the fixed repository and the tag; the registry's `tarball_url` is ignored. The stream and the sum of member sizes are capped at 50 MiB and the archive at 10,000 members; a download has a 120 second deadline. Extraction uses `tarfile` with `filter="data"` plus explicit checks (absolute paths, `..`, devices, hard links with `..` or an absolute target, and symbolic links whose target, read from the link's own directory, is absolute or leaves the single top-level directory, so `.opencode/skills -> ../skills` stays valid; one such link refuses the whole archive, and a second check after extraction repeats the test on the promoted directory), requires exactly one top-level directory and happens in a temporary directory that is removed on failure. Nothing downloaded is executed during extraction.
- **The GitHub tarball has no checksum.** wev cannot tell a genuine release from a tampered one served over a valid connection. For `rea`, wev downloads nothing: `npx` fetches the package into npm's cache during the health check, under npm's own integrity checks, which wev does not verify.
- **The health check catches a broken update, not a malicious one.** For `rea` it runs the new package's MCP server, so a hostile package would already be running code on your machine. `npx` is started without a shell, but the child keeps `PATH`, `HOME`, `LANG`, `LC_*`, `XDG_*`, `npm_config_*` and `NODE_*` from your environment. With `HOME` kept, npm reads `~/.npmrc`; `npm_config_*` may carry npm tokens; and `NODE_OPTIONS` can inject code into the child. The process group is killed after 60 seconds.
- **An update is asked about, not blocked.** The daily check only reports. Claude Code asks before `wev skills update|rollback|freeze|install|activate|deactivate`; on Codex, Gemini CLI and OpenCode they are denied (person only). The model asking you once in the conversation is an instruction (documented only): it does not hold under auto-accept or bypass modes, or for a command the guard cannot parse.
- **MCP replies are bounded.** The health check reads at most 32 MiB per reply line from the server (`reply_too_large` names the limit); the real `tools/list` is about 3.2 MB. A longer line is refused, not truncated.
- **The daily check does network at session start.** `wev skills check --daily` makes a few requests under a 10 second wall-clock budget and prints nothing on any error. A failure does not advance the daily marker; sources that succeeded in a partial failure still save `last_check` and `latest_seen`, and a budget timeout saves nothing. A declined source still makes its registry call before it is skipped.
- **Activation links are tracked.** `activate` creates symlinks in `~/.claude/skills` and `~/.agents/skills` and records them in `manifest.json`. It refuses entries it did not create (including a file you put where a wev link was) and a listed link that no longer points where wev made it point is treated as yours: kept, not replaced or removed. `deactivate` removes only listed links that still point there. An agent in your account can still edit those directories or the manifest directly.
- **The state file is data.** Unknown keys, wrong types and version names outside `[A-Za-z0-9._-]+` are rejected; `current` and `*.tmp-*` are reserved. A version from a registry, or given to `install --version`, must also have the shape of its source (strict semver for npm, `v1.2.3` or `1.2.3` for a GitHub tag, 7 to 40 hex characters for a sha).
- **Self-update is partial.** For `wev-skills`, wev installs and health-checks the new directory only. A wev-skills update does not switch the running plugin: the installer does, and `skills update` does not. A default-branch HEAD install is health-checked only for running and printing a well-formed version.

## rea: reverse-engineering server

`wev rea serve` starts the third-party `rea` MCP server for the harness. Status: implemented and tested with fake `npx` and `docker` executables (unit tests); the real rea server, the real container build and the real harness loaders are not run in this change (e2e part). The same guardrail-not-boundary position applies.

- **rea is "not a sandbox".** rea's own SECURITY file says so, and that opening an untrusted binary runs parsing with your permissions. Its tools can run a command you choose, drive a debugger or a device, and open pages. Treat what the tools return as untrusted text.
- **What the container does and does not isolate.** Isolated mode runs rea in a Docker container as your own uid:gid, with the network on, the working directory mounted read-only at its own path and a wev-owned directory writable at `/opt/rea-home`. That limits what rea can write in the repository and keeps its files out of your home. It is not a boundary against an agent in your account: that agent can run `docker` itself, change the mode through its own file tools, or use the network. The runtime tools (Frida, adb, browser and Electron capture, debuggers) are unavailable there, which is a limit of the mode, not a protection.
- **Direct mode runs rea on the host.** `npx -y rea-agents@<version> mcp` runs with your permissions, with no container.
- **The `rea serve` argv is built from four things only:** the semver version pinned by `wev skills` (a tag such as `latest` or a range is refused), the mode, the checked working directory and the wev-owned home directory. Nothing from the repository or the environment reaches it. The working directory is refused when it is `/`, your home or a parent of it; a path with `:`, `,` or a control character is refused (mount syntax); a symlinked home directory is refused. The process is replaced by `docker` or `npx` without a shell.
- **`docker` and `npx` come from `permissions.exec_path`,** never from `$PATH`, and are refused when their path or its resolved target is inside the repository root. That check says nothing about other writable directories a repository `wev.config.json` may put on `exec_path`.
- **Asks.** In Claude Code the hook asks before `wev rea mode` and `rea build-image`; on Codex, Gemini CLI and OpenCode they are denied (person only). As elsewhere, an ask does not hold under auto-accept or bypass modes.
- **Protected path.** `~/.config/wev-skills` (`rea.json` and the key file) is a protected path in the Bash guard, so the hook treats a Bash command that writes, moves or removes it as protected-path access (ask, or deny in plan mode). The agent's own file tools can still edit it.
- **OpenCode registration is not protected.** The manifest that records wev's `mcp.rea` entry is not a protected path: an agent in your account can edit it, as it can edit `opencode.json` itself. Install and uninstall refuse an entry that does not match the manifest, which is a guardrail and not a boundary.
- **Authorization is yours.** rea's DISCLAIMER says that inspecting a program does not by itself establish permission for every operation, and that you carry the authorization and the legal responsibility for what you direct an agent to do. wev adds no authorization of its own.

## Installer

`install.sh` is a convenience for a person at a terminal, not a control. Status: implemented and tested with fake harness CLIs and a local source (unit tests, offline); the download route, a real `claude plugin install`, the real harnesses, a real JEV probe and the interactive dependency-install path are not run in this change (e2e part). The `curl | bash` form is documented only, until the owner publishes the script.

- **Questions come from the terminal only.** Every prompt reads `/dev/tty`, never stdin (under `curl | bash` stdin is the script). Without a terminal and without `--yes` it stops and names the flags; it does not guess an answer, a key included.
- **Where it writes.** `$XDG_DATA_HOME/wev-skills`, `$XDG_CONFIG_HOME/wev-skills` (key file `.env` and `wev.config.json`, both 0600, in a 0700 directory), a temporary directory removed on exit, and the harness directories the `wev` CLI already writes (Codex, Gemini CLI and OpenCode through `wev harness install`; Claude Code through `claude plugin marketplace add` and `claude plugin install`).
- **The JEV key.** It is read with a hidden prompt and piped to `wev jev key set` on stdin, so it is in no argument, no environment variable, no log and not in the summary. `jev key set` writes through a temp file in the same directory and renames it, refuses a symlinked file or directory, and prints the path and status, never the key. It is a person-only command (asked on Claude Code, denied on the other harnesses). A `TYPESAFE_API_KEY` in the environment still shadows the file (`shadowed_by_env`). The installer then sends one probe question, `installer probe`, to the JEV service with `TYPESAFE_API_KEY` unset, so the typed key is the one validated; when that variable is exported in your shell, the summary says it will win over the stored key. Any failed step ends the run with exit 1, and a failed uninstall step keeps the data directory so the manifests remain for a retry.
- **Trust chain.** The script runs code only from the clone of the pinned release tag (to run `wev skills update wev-skills`, which re-downloads the release through the third-party checks above) and then from `current`. The release tag must be a plain `N.N.N` version, optionally prefixed with `v`. The GitHub tarball has no checksum, so this trusts GitHub and TLS. `--source DIR` is the one way to run code from elsewhere: `DIR/bin/wev` runs with your permissions, so use it only on a tree you have read, and the summary says the install is from a local source, not self-updating. The script has no `eval` and no shell string built from input (grep-level tests).
- **The user configuration tier.** `~/.config/wev-skills/wev.config.json` is read below a repository's `wev.config.json`. It is a protected path in the Bash guard, so a Bash command cannot write it; the agent's own file tools still can. A repository without its own file inherits what the user file sets, `permissions.allowed_commands` included, so keep it to `language` and `decision.provider` unless you mean more. The repository file wins where both set a key, and the trust rules (`decision.jev.command`, `agents.directories`) apply to the merged result.
- **What it never does.** No remote script is piped into a shell to install a dependency. Under `--yes` it installs no system package; otherwise it runs one of five fixed commands (`uv python install 3.14`, `brew install python`, `brew install node`, `sudo apt-get install -y ...`, `sudo dnf install -y ...`) only after you say yes. It leaves to you: Codex hook trust, `gemini extensions link` and `codex mcp add rea -- ...`, printed as next steps.
- **Uninstall** goes through the CLI's manifests and removes the data directory; it keeps the configuration directory (the key file) unless you answer yes or pass `--purge`.

## Known limits

These are open. Do not rely on the engine for any of them.

- **Other tools.** Only the Bash tool passes through the hook. A file edit with Claude Code's own tools is not seen, and that includes edits to the state directory, the approvals file, the audit log, the configuration and the per-user run registry. An agent can forge a grant and the matching audit event, mark a run finished, or edit the registry with those tools (for example add an entry that vouches for a forged run). The hook protects the registry's directory, and asks before a directory above it is moved or removed, only for Bash commands it can read; the agent's own file tools can still edit, move or replace the registry.
- **The terminal prompt.** A process can allocate a pseudo-terminal, read the confirmation word and type it. Without the hook routing these commands to Claude Code's prompt, nothing stands in the way. The hook cannot see inside a script file or a program: a script that types into a pseudo-terminal (for example `python3 pty_type.py`, where the script itself starts the engine on a pseudo-terminal and types the confirmation word) names nothing on the command line the hook reads, so it is not asked about.
- **Scripts and interpreters.** `python3 script.py`, `node x.js`, `make`, `npm test` and any program the classifier does not know run whatever their files say, in execute mode, with no question. A shell running a script file is asked about only when the file is the first operand. The contents of a script are never analyzed.
- **Ordinary mutation in execute mode.** `mv`, `cp`, `sed -i`, redirections and similar commands are how work gets done, so they pass without a question unless they touch a protected path.
- **Unknown programs.** A program at an absolute path outside the working tree is classified by its name only. A renamed or wrapped binary is not recognized.
- **Classification is a heuristic.** It knows a fixed list of programs, subcommands and options. Anything outside the list may be treated as lower risk than it is.
- **Implicit Git helpers.** Explicit `--ext-diff` and `--textconv` options require approval, but repository configuration and attributes can enable helpers even for an ordinary `git diff`. Inspect unfamiliar repositories before trusting read-only Git commands. The [local security review](docs/security-review-2026-10-13.md) records a synthetic reproduction; operating-system isolation is needed to contain arbitrary helpers.
- **The child's environment.** `wev exec` resolves the program on the safe path but the program inherits the caller's environment, including `PATH` for whatever it starts itself.
- **Time of check.** Paths are resolved when a command is judged. A symlink swapped in afterwards is not covered.
- **Hooks can be absent or old.** The hooks act only when the plugin is installed and enabled. Under a Python older than 3.14 the hook exits without checking anything and says so on stderr (one line). The stock macOS `/usr/bin/python3` is 3.9 and is not supported, so the plugin needs the `python3` on `PATH` to be 3.14 or newer. Check with `python3 --version`, and with `command -v python3` to see which one is used.
- **Plan amendments are recorded, not prevented.** `wev plan set` refuses to change the acceptance criteria, checks, files, risk or `read_only` flag of a task that has ever been started, unless it is given `--amend --reason <text>`. Whoever can run `plan set` can amend. An amendment is recorded as a decision and a `plan.amended` audit event, resets that task's verification (a running task must be checked again, a verified one goes back to pending) and is listed in the delivery report under "Plan amendments" with before and after. The engine does not judge whether the new criteria are weaker. Adding tasks and changing tasks never started stays free.
- **The fingerprint and ignored files.** The tree fingerprint covers the commit, the status, staged and unstaged diffs and the size and modification time of untracked files git does not ignore. Files git ignores are outside it by design: a change to them is not seen as work and does not invalidate a verification. `wev plan set` prints a warning when a task's `files` or a check's arguments name an ignored path, and `task check` and the report carry a notice.
- **Run lookup for paths built from variables.** The hook finds the run from its directory, enclosing directories, the paths a command names, and a path that is a parent of a registered run root. A path built from a variable cannot be matched; when no run is found and any run is registered for the user, a command with a `$` expansion in a word is answered `ask`. A command matched to no run is judged under the built-in default policy instead, so what a run's pinned configuration adds (extra protected paths, denied commands) does not apply to it.
- **The report is recomputed at report time, not continuously.** At `wev run report` and `wev run finish` the tree is compared with the one seen at the latest `verified` record. If it differs and no task is running, every verified task whose checks have not passed on the current tree is reported as "verified, then changed" and the overall status is `incomplete` until `wev task check <id>` passes again (the report's `next_step` says so). A change made and reverted between two reports is not seen; while a task is running, changes count as that task's work; for a finished run the report shows what `run finish` recorded.
- **Decision provider.** An external program named in `decision.jev.command` (any value but `builtin`) is run as given; the engine does not verify what that program is. The built-in client sends the redacted state to the https host `JEV_API_URL` names, whatever it is, with a key from `TYPESAFE_API_KEY`; a stored key goes only to the default endpoint (see "Built-in JEV client").
- **Remote hosts.** Once a remote command starts, the host is outside the engine's control. Remote run records live in the state directory and share its limits.
- **Redaction misses**: secrets with no recognizable shape or name (a bare cloud secret key, a value in a whitespace-separated table, netrc and pgpass lines, PuTTY keys); base64 or hex encoded values; prose such as "the password is X"; unquoted values after a space, comma, semicolon or ampersand; YAML next-line and TOML multi-line values; URL passwords containing `@`; short URL user tokens and short bearer tokens; names such as `pw=`, `pass:`, `key=`, `otp`, `pin`, `DSN`; option values that start with a hyphen; clients not on the list (`mongosh -p`, `psql -W`, `zip -P`, `ldapsearch -w`, `curl -d` bodies) and positional passwords; names obfuscated with zero-width or full-width characters; secrets in file names.
- **Untrusted text.** Fencing and scanning do not make instruction-like wording harmless. Paraphrases, other languages and encodings get through the scanner.
- **`scripts/scan_secrets.py`** is a tripwire for obvious mistakes: it misses low-entropy passwords, secrets with no prefix or telling name, UTF-16 without a byte-order mark, split or encoded values, and files under `tests/`.
- **Unattended scoring.** The agent can game its check by editing code that the stored test imports; stored case files are copied back after the agent runs, and a gamed pass can let in a text lesson that passed the filter, which you can retire. Writes to the shared git directory are detected, not prevented: the hardened git calls do not override every configuration key (a filter driver with `.gitattributes`, for one), and detection stops the run. Grandchild processes of the agent can outlive the timeout, because there is no process group. A normal exit removes the scratch worktree with the hardened `git worktree remove`; after an error or detected tampering it is removed with `rmtree` only, so a stale worktree entry can remain (`git worktree prune` clears it). The workspace shares refs and objects with your repository, so the agent's Bash could move branches (`git branch -f`, `git update-ref`); refs are not fingerprinted, and this depends on the hook's verdict on those commands. A score links a lesson to a pass over model runs; that correlation is not proof that the lesson caused it.
- **Workflows** pin their actions to commit SHAs (looked up on 2026-10-13) and Dependabot is configured to propose updates weekly. Consult the repository's Actions history for results tied to a specific commit. A pinned SHA is not a review of the action's code.

## Operating advice

- Run agents with least privilege: a dedicated user or a container, a limited working directory, and no production credentials in the environment.
- Keep the plugin's hooks enabled and answer Claude Code's permission prompts yourself. Read the exact command before you allow it.
- Review the diff before you accept work. The engine records what it was told; the diff shows what happened.
- Never point an agent, or the remote module, at production without a person watching each impactful operation.
- Treat the configuration file and the state directory as sensitive: they decide the policy and hold the record. Keep them out of shared or world-writable locations, and run `wev approval verify` when something looks off.
- Do not put secrets on command lines. Use files or environment variables.
