# Planned experiments

Portuguese version: [experiments.pt-BR.md](experiments.pt-BR.md).
Hypotheses behind these experiments: [hypotheses.md](hypotheses.md). Status of every experiment: **planned, not run**.

## Read this first

- **No improvement numbers exist yet.** wev-skills has no measured results. Nothing in this repository may claim that a default (thresholds, planning policy, tool set) improves success, cost or speed until an experiment below has produced those numbers and they are recorded with the configuration, the model identifiers, the date and the raw outputs.
- **The scripted-agent harness validates harness mechanics only.** The deterministic eval harness (`evaluation.harness.run` with `ScriptedAgent`, see architecture section 4.12) replays fixed action sequences. It can show that thresholds fire at the configured ratios, that pinned items are never elided, that an archived original is returned by id, that the guard trips on an injected loop, and that reports and metrics are computed correctly. It cannot show whether any of these behaviours help a model finish a task, because the scripted agent does not reason. Results from it must be labeled "simulated" in reports.
- **Real-model runs are optional and need a provider.** Unit tests and CI run without a paid model (project constraint). Real-provider runs are executed on demand by the owner, with the model identifiers recorded.
- **Design for the noise the paper did not measure.** The paper ran each task once at temperature 0. For real-model runs, wev-skills should repeat each task several times per configuration and use paired comparisons on task outcomes, reporting intervals rather than single numbers. The number of repeats is not fixed here.

## Notes

- E1 is the only experiment fully answerable without a model. Run it first, and include it in the unit test suite.
- E2 to E4 reproduce, with wev-skills's own context manager, directions the paper reported for its harness (Section 3.2). A result that differs would not contradict the paper, because the harness, models and tasks differ.
- E5 and E6 test the paper's finding that component value depends on model capability. They need at least two model tiers to say anything; with one model they cannot show a crossover.
- E7 includes an engineering safety test (guards trip) and an empirical question (do they harm legitimate runs). The paper offers no evidence on either.
- E8 and E9 have no support in the paper; they test wev-skills's own design choices.
- E10 and E11 test mechanisms added after the first reading of the paper (the plan reminder and the capability profile). The scripted rows for them show selection mechanics only: under `harness.executor_tier: auto` the profile changes nothing by construction, and the hooks that deliver the reminder have not been exercised in a real Claude Code session.
- E12 tests per-task tool selection, which the paper did not study. Its scripted row uses hand-set per-tool constants, so the token figures there are estimates; only the client's reported input tokens in a real run can say whether anything is reduced, and only misses and task success can say what it costs.
- Every report states, for each run, one label from: implemented and tested; implemented but untested; simulated with mocks; documented only; blocked.
