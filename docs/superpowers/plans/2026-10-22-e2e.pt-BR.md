# Plano de Implementação dos Testes de Ponta a Ponta

Versão em inglês: [2026-10-22-e2e.md](2026-10-22-e2e.md).

> **Para agentes de execução:** SUB-SKILL OBRIGATÓRIA: use superpowers:subagent-driven-development (recomendado) ou superpowers:executing-plans para implementar este plano tarefa por tarefa. Os passos usam a sintaxe de caixa de seleção (`- [ ]`) para acompanhamento.

**Objetivo:** `make e2e` roda a coisa de verdade: o instalador contra uma rede real (npm, GitHub), o servidor rea real, a atualização e o rollback reais de terceiros, a desinstalação real — no macOS com um `HOME` isolado e em um contêiner Linux em branco — e, quando o dono mandar, os harnesses reais e uma chave real do JEV. Cada cenário imprime o que vai gastar antes de rodar e se recusa a rodar sem uma confirmação explícita.

**Arquitetura:** os cenários são módulos `unittest` em `tests/e2e/`, ignorados pelo `make test` (eles são importados, mas toda classe é `skipUnless(os.environ.get("WEV_E2E"))`), conduzidos por um pequeno executor `scripts/e2e.py` que lista os cenários com a linha de custo, pede `yes` em um tty (ou `WEV_E2E_CONFIRM=yes`), define `WEV_E2E=<scenario>` e grava um relatório em Markdown em `evals/reports/e2e-<date>.md` com uma linha por verificação e o rótulo de evidência dela. Todo cenário instala por `install.sh --source <este clone>` em uma árvore temporária de `HOME`/`XDG_*` que remove depois, de modo que nada toca a conta do dono a menos que o cenário diga que toca. O cenário Linux roda o mesmo instalador dentro de um contêiner construído a partir de `docker/e2e/Dockerfile` (`python:3.14-slim` + git, curl, node) com o clone montado somente leitura em `/src`.

**Stack Técnica:** biblioteca padrão do Python 3.14 (`unittest`, `subprocess`, `pty`), Docker para o cenário Linux, as CLIs reais `claude`/`codex`/`gemini`/`opencode` somente nos cenários de harness.

**Spec:** [docs/superpowers/specs/2026-10-20-setup-and-third-party-design.md](../specs/2026-10-20-setup-and-third-party-design.pt-BR.md), "Testes de ponta a ponta" e decisões 13 e 17. Interfaces: `install.sh --help`; Parte 4 (`wev skills install|update|rollback|list`, o cliente MCP em `src/wev_skills/third_party/health.py`); Parte 5 (`wev rea serve|status|mode|build-image`); `claude -p` / `--output-format json` (de `claude --help`), `codex exec` (de `codex --help`), `gemini -p -o json` (nota de pesquisa).

## Restrições Globais

- O `make test` continua offline: os módulos e2e são ignorados a menos que `WEV_E2E` nomeie o cenário deles. `tests/e2e/__init__.py` existe; nenhum cenário roda na importação.
- Nada grava fora da árvore temporária, exceto: a imagem Docker `wev-e2e:<short sha>` (cenário Linux) e o arquivo de relatório. Os cenários de harness que precisam tocar a conta real do dono (login do Claude Code, login do Codex) dizem isso na linha de custo e rodam somente depois da confirmação.
- A chave do JEV nunca é digitada por um teste. O cenário `jev` exige que o dono tenha rodado `install.sh --source <clone> --jev` uma vez no `HOME` e2e (o executor imprime o comando exato com o `HOME`/`XDG_*` isolado exportado) e depois verifica `wev jev status` (`usable`, `orchestration: wev`) e uma chamada real `wev jev ask`. Nenhuma chave aparece no relatório.
- Toda verificação registra: o comando, o código de saída, os campos JSON relevantes e o rótulo (`passed`, `failed`, `skipped: <reason>`). Uma verificação que falhou nunca se esconde atrás de um cenário que passou.
- O relatório diz, para cada harness, "testado com HOME isolado no macOS" ou "testado em um contêiner Linux em branco", nunca "máquina limpa" para o macOS (decisão 17). A documentação só pode dizer "compatível com X" depois que o cenário de harness de X passar; até lá ela mantém "não executado".
- O uso de rede é real e esperado aqui (registro do npm, releases do GitHub, api.typesafe.ai no cenário `jev`); o executor imprime essa linha também.
- Lado Python: mypy strict, funções com menos de 50 linhas, arquivos com menos de 400. Assuntos de commit `<type>: <description>`. Sem push sem o ok do dono.

## Cenários

| Cenário | Onde | Gasta | Verificações |
|---|---|---|---|
| `macos-core` | este Mac, `HOME` isolado | somente rede | `install.sh --yes --source <clone> --harness '' --no-jev --rea-mode direct` termina com 0 e zero falhas; `wev version` = versão do clone; `skills list` mostra `rea` e `agent-skills` ativos nas versões mais novas e `wev-skills` não autogerenciado (`--source`); `rea status` modo direct; `jev status` `orchestration: harness`; `wev rea serve` em modo direct responde `initialize` + `tools/list` com pelo menos uma ferramenta (o cliente MCP da Parte 4); os links `~/.claude/skills` e `~/.agents/skills` só existem se esses diretórios já existiam (não existem em um HOME novo: afirmar que nenhum foi criado); rodar de novo com as mesmas flags → código 0, mesmas versões; caminho de atualização: `skills install rea --version <previous release>` e depois `skills rollback rea` → o ativo é a versão anterior, `skills update rea` → a mais nova de novo; caminho quebrado: `skills install rea --version 0.0.0-wev-e2e-broken` → código 8 (o `npx` não consegue baixar) e o ativo não muda; `install.sh --uninstall --yes --purge` → diretórios de dados e de configuração removidos, nada mais sob o `HOME` |
| `macos-isolated` | este Mac, Docker | rede, um `docker build` (minutos) | `--rea-mode isolated` + `rea build-image` → a imagem `wev-rea:<version>` existe; `rea serve` responde `initialize` + `tools/list` a partir do contêiner; uma chamada de ferramenta estática em um arquivo do cwd montado (por exemplo `inspect_artifact` em um ELF ou wasm pequeno de `tests/fixtures/`, o que existir; senão ignorar com o motivo) devolve evidência; a montagem gravável do home guarda o estado do rea depois; o uid de `--user` coincide com o uid do host |
| `linux-core` | contêiner em branco de `docker/e2e/Dockerfile` | rede, um `docker build` | as verificações do `macos-core` dentro do contêiner (`install.sh --source /src`), mais: a verificação de dependências do instalador passa em uma imagem padrão, e a desinstalação não deixa nada no `HOME` do contêiner |
| `claude` | este Mac, `HOME` isolado **e o login do Claude do dono** | conta do Claude Code + tokens | `install.sh … --harness claude` → `claude plugin list` mostra `wev-skills` habilitado; `claude -p "Run /wev-orchestrate with the objective: print the wev version" --output-format json` em um repositório git descartável: o hook rodou (existe uma execução em `.wev/` ou a linha de contexto da sessão aparece na transcrição), as skills `wev-reverse`/`wev-orchestrate` são listadas por `claude plugin list`/pela transcrição, as ferramentas `mcp__rea__*` aparecem na lista de ferramentas da transcrição (uma chamada de ferramenta do `rea` não é obrigatória); `skills check --daily` rodado pelo hook SessionStart deixa o marcador |
| `codex` | este Mac, `HOME` isolado e o login do Codex do dono | conta do Codex + tokens | `install.sh … --harness codex`; a pessoa confia nos hooks quando o Codex pergunta (passo interativo, impresso); `codex exec "print the wev version with the wev skill"` → a linha de hook negado/permitido aparece; `codex mcp list` mostra `rea` depois que a pessoa rodou a linha `codex mcp add` impressa |
| `gemini`, `opencode` | este Mac | o dono instala a CLI antes (ausente hoje) | `harness install`, o `gemini extensions link` impresso, `gemini -p … -o json` / uma execução headless do OpenCode se existir uma (a pesquisa diz que não há: então ignorar com o motivo) |
| `jev` | este Mac, `HOME` isolado com uma chave que o dono digitou | uma chamada `jev ask` | `jev status` usable, `orchestration: wev`; `wev jev ask` em um arquivo de uma pergunta responde; `wev classify` com `decision.provider: jev` registra o provedor `jev` (sem fallback) |
| `update-daily` | este Mac | rede | com o `rea` fixado na versão anterior e o marcador diário removido, o equivalente de `wev hook session-context --source startup` (`skills check --daily`) imprime o aviso de um parágrafo; `skills decline rea` o silencia; `skills update rea --yes` troca de versão |

## Foco da Revisão

1. Isolamento: o `HOME`, o `XDG_CONFIG_HOME`, o `XDG_DATA_HOME` e o `XDG_STATE_HOME` de todo cenário apontam para dentro da árvore temporária; os cenários `claude`/`codex` declaram quais caminhos reais tocam (o login de `~/.claude.json` só é lido do HOME real se o cenário o copiar — não copie; diga que o login precisa existir no HOME isolado e imprima como).
2. Nenhum segredo no relatório nem na saída dos testes (o cenário `jev` remove `TYPESAFE_API_KEY` de qualquer ambiente capturado e nunca imprime o arquivo da chave).
3. O portão de confirmação não pode ser pulado por acidente: `make e2e` sem tty e sem `WEV_E2E_CONFIRM=yes` termina com 2 antes de rodar qualquer coisa; as linhas de custo são impressas primeiro.
4. Uma falha de cenário é reportada, com o comando que falhou e a saída, e a linha do relatório diz `failed`; o executor termina com 1.
