# End-to-End Tests Implementation Plan

Portuguese version: [2026-10-22-e2e.pt-BR.md](2026-10-22-e2e.pt-BR.md).

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `make e2e` runs the real thing: the installer against a real network (npm, GitHub), the real rea server, the real third-party update and rollback, the real uninstall — on macOS with an isolated `HOME` and in a blank Linux container — and, when the owner says so, the real harnesses and a real JEV key. Each scenario prints what it will spend before it runs and refuses to run without an explicit confirmation.

**Architecture:** the scenarios are `unittest` modules under `tests/e2e/`, skipped by `make test` (they import but every class is `skipUnless(os.environ.get("WEV_E2E"))`), driven by a small runner `scripts/e2e.py` that lists the scenarios with their cost line, asks for `yes` on a tty (or `WEV_E2E_CONFIRM=yes`), sets `WEV_E2E=<scenario>`, and writes a Markdown report to `evals/reports/e2e-<date>.md` with one row per check and its evidence label. Every scenario installs through `install.sh --source <this clone>` into a temporary `HOME`/`XDG_*` tree that it removes afterwards, so nothing touches the owner's account unless the scenario says so. The Linux scenario runs the same installer inside a container built from `docker/e2e/Dockerfile` (`python:3.14-slim` + git, curl, node) with the clone mounted read-only at `/src`.

**Tech Stack:** Python 3.14 standard library (`unittest`, `subprocess`, `pty`), Docker for the Linux scenario, the real `claude`/`codex`/`gemini`/`opencode` CLIs only in the harness scenarios.

**Spec:** [docs/superpowers/specs/2026-10-20-setup-and-third-party-design.md](../specs/2026-10-20-setup-and-third-party-design.md), "End-to-end tests" and decisions 13 and 17. Interfaces: `install.sh --help`; Part 4 (`wev skills install|update|rollback|list`, the MCP client in `src/wev_skills/third_party/health.py`); Part 5 (`wev rea serve|status|mode|build-image`); `claude -p` / `--output-format json` (from `claude --help`), `codex exec` (from `codex --help`), `gemini -p -o json` (research note).

## Global Constraints

- `make test` stays offline: e2e modules are skipped unless `WEV_E2E` names their scenario. `tests/e2e/__init__.py` exists; no scenario runs on import.
- Nothing writes outside the temporary tree except: the Docker image `wev-e2e:<short sha>` (Linux scenario) and the report file. Harness scenarios that must touch the owner's real account (Claude Code login, Codex login) say so in their cost line and run only after the confirmation.
- The JEV key is never typed by a test. The `jev` scenario requires the owner to have run `install.sh --source <clone> --jev` once into the e2e `HOME` (the runner prints the exact command with the isolated `HOME`/`XDG_*` exported) and then checks `wev jev status` (`usable`, `orchestration: wev`) and one real `wev jev ask`. No key appears in the report.
- Every check records: the command, the exit code, the relevant JSON fields, and the label (`passed`, `failed`, `skipped: <reason>`). A failed check never hides behind a passed scenario.
- The report says, for each harness, "tested with isolated HOME on macOS" or "tested in a blank Linux container", never "clean machine" for macOS (decision 17). The docs may say "compatible with X" only after the harness scenario for X passed; until then they keep "not run".
- Network use is real and expected here (npm registry, GitHub releases, api.typesafe.ai in the `jev` scenario); the runner prints that line too.
- Python side: mypy strict, functions < 50 lines, files < 400. Commit subjects `<type>: <description>`. No push without the owner's ok.

## Review Focus

1. Isolation: every scenario's `HOME`, `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` point into the temp tree; `claude`/`codex` scenarios state which real paths they touch (`~/.claude.json` login is read from the real HOME only if the scenario copies it — do not; say the login must exist in the isolated HOME and print how).
2. No secret in the report or in the test output (the `jev` scenario redacts `TYPESAFE_API_KEY` from any captured environment and never prints the key file).
3. The confirmation gate cannot be skipped by accident: `make e2e` without a tty and without `WEV_E2E_CONFIRM=yes` exits 2 before anything runs; the cost lines are printed first.
4. A scenario failure is reported, with the failing command and output, and the report row says `failed`; the runner exits 1.
